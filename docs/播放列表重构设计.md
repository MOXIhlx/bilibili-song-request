## 本批实施中发现并修掉的 bug

| 问题 | 根因 |
|---|---|
| **点「播放队列」完全没反应** | `start_next_inner(false)` 的"恢复"分支已经废弃（现在都走 `force_take=true`），于是 `api_player_play` 把恢复的曲目当"下一首"跳过了。改为独立的 `resume_or_start()`。 |
| **恢复后曲目立刻消失** | `is_really_idle()` 无条件清理「有 `current` 但 mpv 空闲」的状态——而"从快照恢复、只显示不播放"恰好就是这个状态。改为只在**确实正在播放**时才清理。 |
| **点播放后卡死不返回** | `load_and_play` 同步 `await` 歌词网络请求，无超时。改为后台拉取（`spawn_lyrics_load`）+ 5 秒超时，并加"过期歌词不覆盖新歌"保护。 |
| **继续播放总是从头** | mpv 的 `seek` 只投递命令；紧跟 `loadfile` 时文件未就绪，跳转被丢弃。改为延迟 1.2 秒后 seek（并跳过已经接近目标的情况）。 |
| **用 `loadfile ... start=<秒>` 会让播放冻结** | 实测加上 `start=` 后位置完全不推进（普通 load 每秒前进）。已放弃该方案。 |

# 第八批修正：上一首/下一首 历史被销毁

## 症状

「上一首」反复提示「没有更多了（已经是第一首）」，即使刚刚才播过好几首。
实测还发现**播放序列会随失败次数变短**（`playing` 从 2 掉到 1）。

## 根因

`load_and_play` 在取不到播放地址（版权受限等）时会调用 `drop_item(item.id)`，
把这条**从 `playing` 播放序列里删除**。

这个"清理"的代价是**历史被销毁**：

- 播不了的歌从序列里消失 → `previous()` 再也回不到它；
- 序列越用越短，最后只剩一首，于是「上一首」永远说"已经是第一首"。

## 修法

失败时**保留条目**，只让游标绕过它：

- 删掉失败分支里的 `drop_item` 调用（`advance` 与 `previous` 本来就会
  跳过加载失败的曲目，坏条目不会再被播放，因为游标不会停在它上面）；
- `step_previous` / `step_next` 只移动游标、不删除条目，因此历史完整保留。

## 实测

```
第1首 オラシオン      playing=1 cursor=0
第2首 你还在不在      playing=2 cursor=1
第3首 仰望            playing=3 cursor=2
上一首 → 你还在不在   cursor=1        ← 修复前这里报「已经是第一首」
上一首 → オラシオン   cursor=0
上一首 → 提示已是第一首，当前曲不动   ← 只剩一首时才是正确提示
下一首 → 你还在不在   cursor=1 playing=3
下一首 → 仰望         cursor=2 playing=3   ← 沿序列前进，不抓新歌
```

新增回归测试 `previous_keeps_history_when_a_song_is_unplayable`，
并给 `MockPlayer` 加了 `fail_urls()` 以便真正走到加载失败分支
（否则测试只覆盖成功路径，这个 bug 永远不会被发现）。

## 教训

# 第十二批：「点歌马上就切歌」+「点歌列表一直是空的」

## 症状

观众一点歌，当前**空闲歌单**的歌立刻被切断；用户把策略改成「播完当前再切」也没用。

## 根因：`current_is_idle` 从来没被正确写入

这个标记决定「有人点歌要不要立刻让位」，但它在**取新歌的分支里压根没写**：

```rust
// ③ 取新歌（旧代码）
match self.take_new_song(skipped_id) {
    Some((item, from_idle)) => {          // ← from_idle 算出来了
        queue::push_playing(&self.state, item.clone());
        self.sync_current_from_playing(); // ← 但没人把它写进 current_is_idle
```

于是从空闲歌单取的歌一直带着 `current_is_idle = false`，连锁后果：

| 表面现象 | 真实原因 |
|---|---|
| 策略怎么改都不切歌 | `should_switch_now` 的第一个条件 `current_is_idle` 恒为 false |
| 空闲书签回归失效 | 同一标记 |
| 顺带发现：`previous()` 会削短历史 | 失败时 `drop_item` 把条目从 `playing` 删掉 |

另外两条加载路径也有同样问题，一并修掉：

- 沿 `playing` 序列前进时沿用旧来源快照 → 改为按条目**实际是否属于空闲歌单**推导（`item_is_from_idle`）；
- 「从上次位置继续」与 `resume_or_start` 直接加载时也没写标记。

## 修法

1. 新增 `item_is_from_idle(item)`：按 `QueueItem.id` 判断条目是否在空闲歌单里；
2. **所有**设置 `current` 的路径（取新歌 / 沿序列前进 / 继续播放 / 恢复后播放）都调用 `mark_current_source`，不再有任何路径"忘记写标记"；
3. `mark_current_source` 增加一条 info 日志，记录 `title` 与 `from_idle`——下次再出这类问题一眼就能定位；
4. 删除 `drop_item`（历史被销毁的元凶），其功能由「游标绕过」取代。

## 实测（模拟弹幕走完整链路）

```

点歌入队            title=青花瓷 position=1
有人点歌，按「立即切换」策略中断当前空闲歌曲          ← 策略生效（之前从不触发）
已标记当前曲目来源 title=青花瓷  from_idle=false     ← 切过去后标记也正确
已按配置切到点歌队列

[after_current] 在播=下雨天  is_idle=true → 点歌后：队列=1  当前=下雨天  未打断=OK
[immediate]     在播=雨爱    is_idle=true → 点歌后：队列=0  当前=青花瓷  已切歌=OK
```

新增 3 个回归测试：`walking_idle_playlist_keeps_current_is_idle_true`、
`immediately_lets_requested_song_cut_in_when_policy_is_immediate`、
`after_current_policy_does_not_cut_in`。

## 过程教训：我的构建验证流程在骗我

这次排查被**陈旧二进制**反复误导——我多次"验证通过/失败"其实跑的都是上一版：

| 坑 | 表现 |

# 第十三批：B 站弹幕「显示已连接，过一会儿自己断掉」

## 症状

弹幕连接能建立、显示已连接，过一会儿自己变成断开。

## 根因：旧连接任务杀不掉，退出后把新连接的状态覆盖了

日志里的固定模式：

```
已请求停止 B 站弹幕客户端
弹幕连接状态变化 status=Stopped
弹幕任务未在 3 秒内退出，已放弃等待      ← 只"放弃等待"，没有真的中止
B 站弹幕连接任务已启动（单连接模式）
B 站弹幕鉴权成功
弹幕连接状态变化 status=Connected
B 站弹幕客户端已退出                    ← 旧任务这时才退
弹幕连接状态变化 status=Stopped          ← 把新连接的 Connected 覆盖成 Stopped
```

三个缺陷叠加：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 连接循环**只阻塞在 `next_frame()`** 上，`stop()` 设的标志要等下一帧（或 90 秒空闲超时）才被检查 | 任务几乎不可能在 3 秒内退出 |
| 2 | 超时后只是"放弃等待"，**没有 `abort()`** | 旧任务继续在后台跑，甚至继续重连，与新连接抢同一条身份码会话 |
| 3 | 客户端写 `AppState` 时**不校验自己是否还是当前连接** | 旧任务退出时把状态写成「已停止」，UI 上就是"刚连上又断了" |

## 修法

1. **可打断的读帧**：连接循环的 `select!` 增加一个停止分支
   （每 100ms 轮询停止标志），`stop()` 能立即结束循环；
2. **真正中止**：`disconnect` 超时后调用 `AbortHandle::abort()`，
   为此在 `RunningTask` 里额外保存 `abort_handle`（`join` 会被 `await` 消耗掉）；
3. **连接代号（`ConnectionEpoch`）**：每次 `connect()` 让 `AppState.bilibili.epoch` +1，
   客户端在创建时记下自己的代号，所有写状态的路径都过 `is_current()`
   ——「已被放弃的旧任务」从此再也改不了界面状态。

## 实测

```
真实身份码连接：24 秒内 6 次采样全部 phase=connected connected=True

连续 4 次重连 + 30 秒稳定观察：
  每次都 phase=connected connected=True
  日志：epoch=ConnectionEpoch(1)…(6) 逐次递增
       「B 站弹幕鉴权成功」×6
       **没有**任何「未在 3 秒内退出」警告
```

新增 2 个回归测试：

- `stop_interrupts_a_blocked_read`：用一个"永不返回帧"的假连接，
  断言 `stop()` 能在 2 秒内打断循环并释放连接；
- `stale_client_cannot_overwrite_connection_state`：代号变化后，
  旧客户端写 `Stopped` / 错误信息都被丢弃，新连接的 `Connected` 保持不变。

## 1. 要解决的问题

### 1.1 现象

用户报告：「点击下一首两次，播放到第三首之后，点一下上一首回到第二首，再点下一首，
播放的**不是第三首而是第四首**。」

### 1.2 根因：同一批歌存在两套互不相干的结构

| 操作 | 当前遍历的结构 |
|---|---|
| 上一首 | `history`（已播历史，**头插**） |
| 下一首 | 先 `history`，回不去再去 `queue`（点歌队列）→ `idle`（空闲歌单） |

两个结构各存一份数据、各自维护"下一个是谁"，于是：

- **`history` 是头插数组**（`insert(0, item)`），每播一首新歌，**所有已有下标整体后移**，
  而 `history_cursor` 存的是**绝对下标** → 位置失真。
- **`history` 上限 30 条**，从**尾部截断**，游标不随之修正 → 超过 30 首后位置错乱。
- **`skip()` 硬编码 `switch_to(item, true)`**（`controller.rs`），
  无论这首歌来自点歌还是空闲，都标记成"空闲歌单来源"，污染后续取歌判断。
- `queue` 与 `history` 中同一首歌各有一份 → "下一首该看哪份"不确定。

### 1.3 结论

不是容器选错（两边都是 `Vec`），而是**事实来源有两个**。必须收敛成一个。

## 2. 已确认的设计决定

| # | 决定 | 说明 |
|---|---|---|
| 1 | 空闲歌单与点歌列表**分开存**（曲库 vs 待播） | 用户最初想法，保留 |
| 2 | 新增 `playing` 播放序列，**只追加、不覆盖** | 不采用"空闲列表赋值给播放列表"（会产生副本） |
| 3 | 新歌**播到末尾时才追加**（方案 1A） | 新歌入队不移动游标 |
| 4 | 有人点歌的切换沿用现有 `idle_switch_policy`（方案 2A/B） | `immediate` 立刻切；`after_current` 播完再切 |
| 5 | `playing` 上限 **200**，只从 `cursor` **左边**回收 | 绝不回收右侧（否则丢失"可前进"的歌） |
| 6 | 保留 `current` 字段（前端零改动） | 每次切歌后同步为 `playing[cursor]` 的克隆 |
| 7 | 重头播 = `seek 0` 后**继续播放**（不是暂停待播） | |
| 8 | 记录"空闲歌单当前播的曲子"，点歌队列空时**回到这首并重头播** | 新增需求，需要两个索引（见 §3.2） |

## 3. 目标数据模型

### 3.1 三个列表 + 游标

```
request : Vec<QueueItem>    点歌队列（待播的新歌，会被消费）
idle    : Vec<QueueItem>    空闲歌单（曲库，永不消费）
playing : Vec<QueueItem>    实际播放顺序（只追加，不覆盖）

cursor       : usize            正在播 playing[cursor]
frontier     : usize            已生成到 playing 的哪个位置（见 §4 规则 2）
idle_current : Option<usize>    空闲歌单书签：正在播/最近播过的空闲歌下标
idle_next    : usize            空闲歌单"下一次取歌"的下标
```

三个区间的语义：

```
        已播区              当前         待播区
┌────┬────┬────┬──────────┬────┬────┬────┐
│ 0  │ 1  │ 2  │    3     │ 4  │ 5  │ 6  │
└────┴────┴────┴──────────┴────┴────┴────┘
                  ↑
                cursor
```

- **上一首** = `cursor -= 1`，播 `playing[cursor]`
- **下一首** = `cursor += 1`，播 `playing[cursor]`；已在末尾则按规则 2 取新歌
- 两个操作读写**同一个数组**，天然对称，不可能再"一个走这个列表、一个走那个列表"

### 3.2 为什么空闲歌单需要两个索引

需求「继续当前播的曲子并**重头播**」拆成两件事：

| 字段 | 含义 | 用途 |
|---|---|---|
| `idle_current` | **正在播/最近播过**的空闲歌下标 | 点歌队列空时回到这首，**重头播** |
| `idle_next` | **下一次从空闲歌单取歌**的下标 | 正常推进，避免重播 |

⚠️ 现有 `idle_cursor` 语义是"下一次取哪首"（取完 `+1`），**不是**"当前在播哪首"。
两者差 1，混用会表现为"回来时跳过一首"。所以必须拆成两个字段。

## 4. 状态机规则

| # | 事件 | 行为 |
|---|---|---|
| 0 | 启动 | `cursor=0`、`frontier=0`、`playing=[]`、`idle_current=None`、`idle_next=0` |
| 1 | 需要播下一首（自然播完 / 点下一首） | ① `cursor+1 < playing.len()` → 播 `playing[cursor+1]`，`cursor+=1`<br>② 否则走规则 2 |
| 2 | 取新歌 | `request` 非空 → `request.remove(0)`（点歌优先）<br>`request` 空 → 取 `idle[idle_next]`，记 `idle_current=idle_next`，按 `idle_mode` 推进 `idle_next`<br>取到的歌**追加**到 `playing`，`cursor = 新下标`，`frontier = cursor+1` |
| 3 | 上一首 | `cursor>0` → `cursor-=1`，播 `playing[cursor]`；否则提示"没有上一首" |
| 4 | 新歌入队（弹幕/主播点歌） | 只 push 进 `request`。**不动 `cursor`、不动 `playing`** |
| 5 | 有人点歌时的即时切换 | 正在播空闲歌曲 且 策略=`immediate` → 立刻按规则 2 取新歌播；`after_current` → 等这首播完 |
| 6 | **点歌队列空了，回到空闲歌单** | **回到 `idle_current` 那首并重头播**（不取 `idle_next`）；播完后再按 `idle_next` 继续 |
| 7 | 手动选空闲歌单某首播 | `idle_current=该下标`，`idle_next=按模式推进后的位置`，追加到 `playing` |
| 8 | 删除条目 | 从 `playing` 删除 → `cursor` 相应左移；从 `idle` 删除下标 `< idle_next` 的 → `idle_next-=1`，并修正 `idle_current` |
| 9 | `playing` 超过 200 | 只从 `cursor` **左边**丢弃最老的 `n` 条，`cursor -= n`、`frontier -= n`；**右侧不动** |

### 4.1 完整场景推演

初始：`request=[B,C,D]`，`idle=[夜曲,稻香,晴天]`，`idle_next=0`，正在播 **A**

```
① 下一首  → request 取 B，playing=[A,B]，cursor=1
② 下一首  → request 取 C，playing=[A,B,C]，cursor=2
③ 上一首  → cursor=1，播 B
④ 下一首  → cursor=2，播 C                    ✓ 回到第三首（用户要的）

⑤ C 播完  → cursor 在末尾 → 取新歌：request 非空 → 取 D
             playing=[A,B,C,D]，cursor=3

⑥ D 播完  → request 空 → 走空闲歌单：
             idle_current=None（还没播过空闲）→ 取 idle[0]=夜曲（idle_next=0）
             playing=[A,B,C,D,夜曲]，cursor=4
             idle_current=0，idle_next=1

⑦ 有人点歌 E → request=[E]（不动 cursor）
            策略 immediate → 立刻播 E：playing=[...,夜曲,E]，cursor=5
            策略 after_current → 等夜曲播完再播 E

⑧ 点歌队列又空 → 回到 idle_current=0 的《夜曲》【重头播】，而不是取 idle_next=1 的《稻香》
             playing=[A,B,C,D,夜曲,E,夜曲]，cursor=6
             之后继续 → idle_next=1 → 稻香
```

## 5. 边界处理

| 情况 | 处理 |
|---|---|
| `idle_current` 那首被删 | 退回 `idle_next`，并提示 |
| 空闲歌单被"覆盖导入"换了内容 | `idle_current`/`idle_next` 重置为 0（避免错位） |
| `idle_mode` = 随机/单曲循环 | `idle_next` 由现有 `idle_next_index()` 决定；`idle_current` 始终记实际播的那首 |
| 队首插队（主播优先） | 只影响 `request` 内部插入位置，与 `playing`/`cursor` 无关 |
| 重启 | 存 `playing + cursor + frontier + idle_current + idle_next`；追加式序列下标稳定，`cursor` 仍指向同一首 |
| 加载失败 | 该条从 `playing` 与来源列表移除，`cursor` 回退一位后继续尝试 |

## 11. 实测结论：哪些东西根本没被保存

在 `%APPDATA%\bilibili-song-request\` 下的实际文件：

|---|---|

| `queue.json` | 9.58KB，顶层键**只有** `version, play_mode, queue, history` |
| `backgrounds/` | 6 个背景图（正常） |

### 11.1 逐项核对

| 用户诉求 | 现状 | 原因（代码位置） |
|---|---|---|
| 保存个性化设置 | ✅ **设置页保存是好的** | `PUT /api/config` → `next.save_to(&ctx.config_path)`（`server.rs:1963`）。实测改 `max_queue=9` 后文件立即更新 |
| **保存音量** | ❌ **不落盘** | `api_player_volume` 只 `s.player.volume = volume`（`server.rs:2038`），**从不调用 `save_to`**。实测：接口改 55 → 内存 55、文件仍 80、文件时间未变 |
| **播放模式** | ❌ **不落盘** | `api_player_mode` 同样只改内存（`queue.json` 里的 `play_mode` 只在队列内容变化时才被 `spawn_queue_persister` 顺带写入） |
| **播放器显示上次的歌** | ❌ 恢复时被清空 | `QueueStore::restore()` 里 `s.current = None`（`store.rs:149`）——即使存了也不恢复 |
| **空闲歌单保留** | ❌ **快照里根本没有 idle** | `QueueSnapshot` 只有 `queue`/`history`/`play_mode`（`store.rs:24`）。实测 `queue.json` 无 `idle` 键 |

### 11.2 一句话总结

> **`config.json`（设置）是好的；`queue.json`（播放状态）缺一大半字段，而且多个接口改了状态却不触发落盘。**
> 所以"设置被重置"的体感主要来自：音量、播放模式、当前歌曲、空闲歌单、点歌日志——这些**从来没被存过**。

# 实施记录（实际改了什么）

## 17. 最终数据模型

```rust
// AppState
queue: Vec<QueueItem>,    // 点歌队列：待播的新歌（会被消费）
playing: Vec<QueueItem>,  // 实际播放序列：只追加，cursor 指向当前
cursor: usize,
idle: Vec<QueueItem>,     // 空闲歌单曲库（永不消费）
idle_current: Option<usize>, // 书签：正在播的那首（重头播用）
idle_next: usize,            // 下一次取歌位置
idle_pending_return: bool,   // 是否被点歌打断、等待回去重头播
```

「上一首 / 下一首」都只是 `cursor ∓ 1`，读写同一个 `playing`。

## 18. 实施过程中发现并修掉的额外 bug

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | 重启后 `playing=True` 但没有声音 | `sync_paused` 用 `playing = !paused && current.is_some()`，而 mpv 启动时会发一次 `pause=false` 初值 | 只用旧 `paused` 判定"真暂停被解除"，从未播放过的曲目不受影响 |
| 2 | `current` 为空但 `playing[cursor]` 有值 | `push_playing` 按 id 去重并**回退游标**，而那条已被回收 | 去掉去重，只追加；"不重播当前曲"改在取歌侧解决 |
| 3 | 解析完成后界面仍显示占位歌名 | 解析器只回写 `playing`，`current` 是解析前的副本 | `sync_current_from_playing` 比对 `song.id`/标题后刷新；解析事件触发一次 |
| 4 | 解析结果写不回 | `item_exists`/`with_item_mut` 没查 `playing` | 四个位置（queue/idle/playing/current）全查 |
| 5 | **「上一首」报 409 / 请求失败** | 上一首版权受限播不了，失败后游标留在坏条目、`current` 被清空 | 失败时按 **id** 还原游标与 `current`，只报错不改状态 |
| 6 | 单曲循环下点「跳过」没反应 | `advance()` 的单曲循环分支没区分"播完"与"用户跳过" | `skipped` 时把当前曲摘出 `playing` 再前进 |
| 7 | 同一首歌在 `playing` 里出现两条 | `next_candidate` 在 RepeatOne 下返回"当前曲"，被当成新歌追加 | 取新歌一律按队列顺序，绝不返回当前曲 |
